## 1. 项目概述

### 1.1 项目背景

传统软硬件项目开发中，跨角色协作存在信息断层、需求溯源困难、进度不透明等问题。本系统旨在构建一个 \*\* 以 Git 为单一事实源（Single Source of Truth）\*\* 的多 AI Agent 协作平台，让每个技术角色由独立 Agent 承担，通过结构化通信和版本化提交实现端到端可追溯的项目管理。

### 1.2 核心目标



| 目标     | 描述                                  | 验收标准                                      |
| ------ | ----------------------------------- | ----------------------------------------- |
| 角色完备   | 覆盖 IPD 全流程技术角色，每个角色对应独立 Sub-Agent   | 角色清单≥15 个技术角色，无销售 / 市场角色                  |
| 版本溯源   | 所有 Agent 交互、需求变更、任务完成均绑定 Git Commit | 任意需求可追溯至发起方 Commit、接收方 Commit、处理结果 Commit |
| 并行协作   | Sub-Agent 间可按需通信，支持异步需求传递           | 通信记录包含双方版本号、需求内容、状态、时间戳                   |
| 用户可控   | 用户可直接与任意 Sub-Agent 交互，实现细节微调        | 用户消息同样进入通信记录，绑定版本号                        |
| 可视化    | 基于 Git Commit 节点的项目看板，展示 Agent 交互拓扑 | 看板可按阶段 / 角色 / 时间筛选，交互链路可点击溯源              |
| GUI 操作 | 所有用户与 Agent 操作均在图形界面完成              | 无需命令行即可完成项目创建、任务分配、代码查看、看板浏览              |

### 1.3 设计原则



1. **Git 即真相**：所有产出物、决策、交互均以 Git Commit 为锚点，不维护脱离版本控制的状态

2. **角色自治**：每个 Sub-Agent 拥有独立仓库、独立上下文、独立决策能力，主 Agent 不越权干预子任务执行细节

3. **通信即文档**：Agent 间的每一次交互都是结构化文档，自动归档并可检索

4. **需求驱动**：所有工作项必须关联明确的需求来源（用户 / 上游 Agent / 评审反馈）

5. **渐进式细化**：主 Agent 先做顶层 WBS 拆解，Sub-Agent 在执行中进一步细化子任务

### 2.2 核心组件职责



| 组件              | 职责                                                       | 关键技术选型建议                       |
| --------------- | -------------------------------------------------------- | ------------------------------ |
| **GUI 应用层**     | 用户与系统的唯一交互入口，提供看板、聊天、代码浏览、追溯四大视图                         | Electron + React/Vue，或纯 Web 应用 |
| **主 Agent 调度器** | 接收用户需求，执行 WBS 拆解，创建 / 唤醒 Sub-Agent，监控全局进度                | LLM + 任务规划链                    |
| **Sub-Agent 池** | 管理各角色 Agent 的生命周期、上下文隔离、并发执行                             | Agent 容器 / 进程隔离，每个 Agent 独立会话  |
| **通信总线**        | 路由 Agent 间消息，记录通信元数据，支持同步 / 异步模式                         | 本地消息队列 + 持久化存储                 |
| **Git 操作服务**    | 统一封装所有 Git 操作（clone/commit/branch/merge/tag/diff），确保提交规范 | libgit2 / isomorphic-git       |
| **需求管理服务**      | 需求的创建、分配、状态追踪、溯源链维护                                      | 基于 Git Issue / 自定义结构化文件        |
| **看板数据聚合**      | 从 Git 历史和通信记录中聚合看板数据，支持多维度查询                             | 增量索引 + 缓存                      |

### 2.3 数据流



```
用户输入需求

&#x20;   │

&#x20;   ▼

主Agent解析 → WBS拆解 → 生成项目计划(写入主Repo)

&#x20;   │

&#x20;   ├──→ 创建Sub-Agent实例（按角色）

&#x20;   │         │

&#x20;   │         ▼

&#x20;   │    Sub-Agent执行任务 → 写入各自Repo → Commit（关联需求ID）

&#x20;   │         │

&#x20;   │         ├──→ 向其他Sub-Agent发需求（通信总线记录）

&#x20;   │         └──→ 向主Agent汇报进度（Commit + 状态更新）

&#x20;   │

&#x20;   ▼

主Agent聚合 → 更新主Repo（submodule引用/产物汇总）

&#x20;   │

&#x20;   ▼

看板数据聚合 → GUI渲染
```

## 3. IPD 流程与技术角色体系

### 3.1 IPD 六阶段与技术活动映射

本系统严格遵循 IPD（集成产品开发）六阶段流程，**仅聚焦技术实现角色**，排除销售、市场等非技术角色。



| 阶段                      | 核心目标              | 关键技术活动                              | 决策评审点         |
| ----------------------- | ----------------- | ----------------------------------- | ------------- |
| **概念阶段** (Concept)      | 定义 "做什么"，验证技术可行性  | 需求分析、技术可行性评估、系统概念设计、关键技术预研          | CDCP（概念决策评审点） |
| **计划阶段** (Plan)         | 定义 "怎么做"，制定详细技术方案 | 系统架构设计、详细技术方案、资源估算、风险评估、测试策略        | PDCP（计划决策评审点） |
| **开发阶段** (Development)  | 完成产品详细设计与实现       | 各模块详细设计、编码 / RTL 设计、单元验证、模块集成、渐增构建  | TR4（开发完成评审）   |
| **验证阶段** (Verification) | 确认产品满足需求          | 系统集成测试 (SIT)、性能验证、可靠性测试、BUG 修复、试产准备 | TR5（验证完成评审）   |
| **发布阶段** (Release)      | 量产 / 上线准备         | 量产导入、生产工艺固化、技术文档定稿、发布评审             | GA（通用可用发布）    |
| **生命周期** (Lifecycle)    | 持续维护与演进           | BUG 修复、版本迭代、技术支持、EOL 评估             | —             |

## 4. Agent 体系设计

### 4.1 主 Agent（LPDT Agent）

#### 4.1.1 定位

主 Agent 是项目的**唯一入口和全局协调者**，承担 IPD 流程中的 LPDT（产品开发团队经理）角色。用户所有项目级需求首先进入主 Agent。

#### 4.1.2 核心能力



1. **需求解析与 WBS 拆解**：将用户自然语言需求转化为结构化的项目计划，按 IPD 阶段拆解为可分配的工作包

2. **角色激活与 Agent 创建**：根据项目类型动态激活所需 Sub-Agent 角色，初始化各自仓库

3. **任务分配与依赖管理**：识别任务间依赖关系，按拓扑序分配任务，管理关键路径

4. **全局进度监控**：聚合各 Sub-Agent 的 Commit 和状态，维护项目级进度视图

5. **风险识别与升级**：检测进度延迟、依赖阻塞、质量问题等风险，触发预警和干预

6. **评审决策支持**：在各 DCP/TR 评审点汇总材料，给出评审建议

7. **主仓库维护**：通过 submodule 或产物汇总方式维护项目主仓库

#### 4.1.3 主 Agent 不做的事



* 不直接编写具体模块的代码 / 设计（那是 Sub-Agent 的职责）

* 不绕过 Sub-Agent 直接修改其子仓库内容

* 不替用户做技术选型决策（提供建议，用户确认）

### 4.2 Sub-Agent 通用规范

#### 4.2.1 每个 Sub-Agent 必须具备的能力



| 能力         | 描述                                               |
| ---------- | ------------------------------------------------ |
| **角色专业知识** | 具备对应技术角色的领域知识、设计规范、最佳实践                          |
| **任务执行**   | 接收需求后，自行拆解为子任务，逐步执行并产出交付物                        |
| **Git 操作** | 所有产出物写入自己的仓库，按规范 Commit，维护分支策略                   |
| **需求管理**   | 维护自己的需求列表（已完成 / 进行中 / 待完成 / 阻塞），记录需求来源           |
| **通信能力**   | 可向其他 Agent（含主 Agent）发送需求 / 反馈，可接收并响应其他 Agent 的需求 |
| **自检与验证**  | 完成任务后执行角色相关的验证 / 检查，确保产出物质量                      |
| **进度汇报**   | 定期或在关键节点向主 Agent 汇报进度、风险、依赖                      |

#### 4.2.2 Sub-Agent 生命周期



```
创建(主Agent触发)

&#x20;   │

&#x20;   ▼

初始化（克隆/创建仓库、加载角色Prompt、读取项目上下文）

&#x20;   │

&#x20;   ▼

待命（接收任务/需求）

&#x20;   │

&#x20;   ├──→ 执行任务 → 产出物Commit → 自检 → 汇报

&#x20;   │         │

&#x20;   │         └──→ 需要协作 → 向其他Agent发需求 → 等待响应 → 继续

&#x20;   │

&#x20;   ▼

项目阶段完成 → 进入下一阶段待命 / 休眠

&#x20;   │

&#x20;   ▼

项目结束 → 归档（仓库冻结、上下文保存）
```

#### 4.2.3 Sub-Agent 上下文隔离



* 每个 Sub-Agent 拥有**独立的会话上下文**，不与其他 Agent 共享内存

* Agent 间信息传递**仅通过通信总线**，不直接读取对方上下文

* 每个 Sub-Agent 可以访问：自己的仓库、项目主仓库（只读）、通信记录（与自己相关的）

* Sub-Agent**不可直接访问**其他 Sub-Agent 的仓库（如需引用，通过通信请求获取指定版本的产物）

### 4.3 Agent 间协作模式

#### 4.3.1 主从模式（主 Agent → Sub-Agent）

主 Agent 分配任务给 Sub-Agent，Sub-Agent 执行后汇报。这是最主要的协作模式。



```
主Agent: 分配任务（含需求描述、验收标准、截止时间、依赖）

&#x20;   │

&#x20;   ▼

Sub-Agent: 确认接收 → 拆解子任务 → 执行 → Commit → 自检

&#x20;   │

&#x20;   ▼

Sub-Agent: 汇报结果（含Commit Hash、完成内容、遗留问题、下一步建议）

&#x20;   │

&#x20;   ▼

主Agent: 验证结果 → 更新项目计划 → 分配后续任务
```

#### 4.3.2 对等模式（Sub-Agent ↔ Sub-Agent）

Sub-Agent 在执行中需要其他角色的输入时，直接向对应 Agent 发起需求。



```
Agent-A（如SE）: 向Agent-B（如EE）发起接口需求

&#x20;   │  内容：接口规格、期望交付时间、关联Commit

&#x20;   ▼

Agent-B: 接收 → 评估可行性 → 接受/拒绝/反提议

&#x20;   │

&#x20;   ▼

Agent-B: 执行 → Commit → 回复Agent-A（含Commit Hash、交付物路径）

&#x20;   │

&#x20;   ▼

Agent-A: 验证接口 → 集成 → 继续自己的任务
```

#### 4.3.3 广播模式（主 Agent → 所有 Sub-Agent）

主 Agent 需要通知全局变更时（如需求变更、计划调整、评审通知），向所有活跃 Agent 广播。



```
主Agent: 广播通知（含变更内容、影响范围、要求响应时间）

&#x20;   │

&#x20;   ▼

各Sub-Agent: 评估影响 → 回复确认/提出异议 → 调整自己的计划
```

## 6. Agent 间通信协议

### 6.1 通信记录数据结构

每一次 Agent 间交互（包括用户与 Sub-Agent 的直接交互）都生成一条结构化通信记录，持久化存储并可追溯。



```
communication:

&#x20; id: COMM-00042                          # 全局唯一通信ID

&#x20; timestamp: "2026-09-04T14:30:25+08:00" # 发起时间

&#x20; type: request                            # request / response / notification / inquiry

&#x20; priority: high                           # critical / high / medium / low

&#x20; status: pending                          # pending / accepted / rejected / in\_progress / completed / blocked

&#x20; # 发起方信息

&#x20; from:

&#x20;   agent\_type: sub\_agent                  # user / main\_agent / sub\_agent

&#x20;   role: system\_engineer                  # 角色名称（user时为"user"）

&#x20;   agent\_id: agent-se-001                 # Agent实例ID

&#x20;   repo: agent-se                          # 发起方仓库名

&#x20;   commit: a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6e7f8a9  # 发起方当前Commit Hash

&#x20;   branch: feature/axi-interface          # 发起方当前分支

&#x20; # 接收方信息

&#x20; to:

&#x20;   agent\_type: sub\_agent

&#x20;   role: hardware\_engineer

&#x20;   agent\_id: agent-ee-001

&#x20;   repo: agent-ee

&#x20;   commit: b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6e7f8a9b0  # 接收方当前Commit Hash（接收时记录）

&#x20;   branch: main

&#x20; # 通信内容

&#x20; subject: "AXI4-Lite接口时钟域需求"       # 主题

&#x20; description: |                            # 详细需求/内容

&#x20;   我在实现AXI4-Lite从机接口时，需要确认以下硬件相关需求：

&#x20;   1. 接口工作时钟频率预期是多少？

&#x20;   2. 是否需要支持异步时钟域跨越？

&#x20;   3. 复位策略是同步复位还是异步复位？

&#x20;   请提供硬件规格说明，以便我完成RTL设计。

&#x20; # 关联信息

&#x20; references:

&#x20;   requirement\_ids: \["REQ-NPU-0023"]      # 关联需求

&#x20;   task\_ids: \["TASK-NPU-0045"]             # 关联任务

&#x20;   related\_comm\_ids: \["COMM-0038"]         # 关联的其他通信

&#x20;   files:                                   # 引用的文件（相对仓库路径+版本）

&#x20;     - repo: agent-se

&#x20;       path: src/axi\_lite\_slave.v

&#x20;       commit: a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6e7f8a9

&#x20; # 响应信息（接收方回复后填充）

&#x20; response:

&#x20;   timestamp: "2026-09-04T15:12:08+08:00"

&#x20;   commit: c3d4e5f6a7b8c9d0e1f2a3b4c5d6e7f8a9b0c1  # 响应时接收方的Commit

&#x20;   summary: |

&#x20;     已确认硬件规格：

&#x20;     1\. AXI接口时钟频率为100MHz

&#x20;     2\. 需要支持异步时钟域（与核心时钟500MHz跨域）

&#x20;     3\. 采用异步复位、同步释放策略

&#x20;     详细规格见 docs/hw\_spec\_axi.md，已Commit。

&#x20;   delivered\_files:

&#x20;     - repo: agent-ee

&#x20;       path: docs/hw\_spec\_axi.md

&#x20;       commit: c3d4e5f6a7b8c9d0e1f2a3b4c5d6e7f8a9b0c1

&#x20; # 闭环验证（发起方确认收到并验证后填充）

&#x20; closure:

&#x20;   confirmed\_by: system\_engineer

&#x20;   timestamp: "2026-09-04T15:45:30+08:00"

&#x20;   commit: d4e5f6a7b8c9d0e1f2a3b4c5d6e7f8a9b0c1d2

&#x20;   result: accepted                         # accepted / rejected / needs\_revision

&#x20;   notes: "规格已确认，已集成到RTL设计中"
```

### 6.2 通信类型



| 类型             | 用途                     | 是否需要响应 | 示例                        |
| -------------- | ---------------------- | ------ | ------------------------- |
| `request`      | 向其他 Agent 提出需求 / 请求交付物 | 是      | SE 向 EE 请求硬件接口规格          |
| `response`     | 对 request 的回复          | 否      | EE 回复硬件规格                 |
| `notification` | 通知 / 广播（不需要回复）         | 否      | 主 Agent 通知阶段评审时间          |
| `inquiry`      | 咨询 / 询问（轻量级，期望快速回复）    | 是      | SWE 向 DRV 询问驱动 API 用法     |
| `review`       | 评审请求 / 评审意见            | 是      | PQA 向 SE 发起设计评审           |
| `escalation`   | 问题升级（通常发给主 Agent）      | 是      | Sub-Agent 遇到阻塞向主 Agent 升级 |

### 6.3 通信状态机



```
&#x20;                   ┌──────────┐

&#x20;                   │ pending  │  发起方创建

&#x20;                   └────┬─────┘

&#x20;                        │

&#x20;             ┌──────────┼──────────┐

&#x20;             ▼          ▼          ▼

&#x20;        ┌────────┐ ┌────────┐ ┌────────┐

&#x20;        │accepted│ │rejected│ │ blocked│

&#x20;        └───┬────┘ └────────┘ └───┬────┘

&#x20;            │                       │

&#x20;            ▼                       │

&#x20;       ┌───────────┐                │

&#x20;       │in\_progress│                │

&#x20;       └───┬───────┘                │

&#x20;           │                        │

&#x20;           ▼                        │

&#x20;      ┌──────────┐                  │

&#x20;      │completed │                  │

&#x20;      └───┬──────┘                  │

&#x20;          │                         │

&#x20;          ▼                         │

&#x20;     ┌───────────┐  发起方确认      │

&#x20;     │  closed   │◄─────────────────┘

&#x20;     └───────────┘
```

### 6.4 通信记录的持久化与索引



* **存储位置**：通信记录同时存储在两处

1. 独立的通信记录 DB（SQLite/LevelDB），用于快速查询和看板聚合

2. 主仓库的 `.project-agent/communications/` 目录下，以 `COMM-{id}.yaml` 文件形式归档，纳入版本控制

* **索引方式**：按以下维度建立索引


  * 通信 ID

  * 发起方角色 / 接收方角色

  * 关联需求 ID / 任务 ID

  * 时间范围

  * 状态

  * 关联 Commit Hash

### 6.5 用户与 Sub-Agent 直接交互

用户直接向 Sub-Agent 提问或下达指令时，同样生成通信记录：



* `from.agent_type = "user"`

* `from.role = "user"`

* `from.commit` 字段记录用户操作时主仓库的当前 Commit（作为用户操作的版本锚点）

* 通信内容记录用户的原始输入

* Sub-Agent 的回复同样记录 Commit 和交付物

这确保了**用户的每一次微调操作都可追溯**，不会出现 "用户私下改了什么" 的信息黑洞。

## 7. 需求管理与 Commit 规范

### 7.1 需求层级结构



```
项目级需求 (Project Requirement)

&#x20;   │  来源：用户输入 / 市场需求（本系统不处理市场，仅用户）

&#x20;   ▼

阶段级需求 (Phase Requirement)

&#x20;   │  来源：主Agent在WBS拆解时分配

&#x20;   ▼

角色级需求 (Role Requirement)

&#x20;   │  来源：主Agent分配 / 其他Agent的request

&#x20;   ▼

任务 (Task)

&#x20;   │  来源：Sub-Agent自行拆解

&#x20;   ▼

子任务 (Sub-Task)

&#x20;   │  来源：Sub-Agent执行中的进一步细化

&#x20;   ▼

Commit (原子交付)

&#x20;      来源：Agent完成一项具体工作后的提交
```

```
&#x20;   comm\_id: null                          # 如果来自Agent间通信，关联COMM-ID
```

### 7.3 需求 - Commit 追溯链

每个需求的完整生命周期可以通过以下链路追溯：



```
需求创建(REQ-0023)

&#x20; → 主Agent分配（Commit: plan类型，关联REQ-0023）

&#x20;   → Sub-Agent接收（Commit: comm类型，关联COMM-xxx）

&#x20;     → Sub-Agent拆解任务（Commit: 写入tasks.yaml）

&#x20;       → 子任务1完成（Commit: feat类型，关联TASK-0045）

&#x20;       → 子任务2完成（Commit: feat类型，关联TASK-0046）

&#x20;       → ...

&#x20;     → 需求完成（Commit: 标记REQ-0023状态为completed）

&#x20;   → 主Agent验证（Commit: review类型，验证结果）

&#x20; → 需求关闭（Commit: 主仓库更新需求状态）
```

### 7.4 任务完成时的 Commit 要求

每个 Agent 在完成一项任务时，Commit 必须包含以下信息（已在 5.4 节 Commit 规范中定义，此处强调执行要求）：



1. **完成的需求**：明确列出本次 Commit 完成了哪些需求 / 子需求

2. **待完成的需求**：列出仍未完成的相关需求及原因（依赖阻塞、技术难点等）

3. **需求来源**：每个完成的需求必须标注来源（用户 / 主 Agent / 其他 Agent 通信 / 评审反馈）

4. **自检结果**：本次产出物的自检 / 验证结果

5. **下一步建议**：建议的后续动作（可选但推荐）

## 8. 用户交互设计

### 8.1 用户交互入口

用户在 GUI 中可以通过以下方式与系统交互：



| 交互方式          | 入口             | 描述                                   |
| ------------- | -------------- | ------------------------------------ |
| **项目级对话**     | 主聊天面板          | 用户与主 Agent 对话，提出项目需求、询问全局进度、做项目级决策   |
| **角色级对话**     | Sub-Agent 聊天面板 | 用户直接与指定 Sub-Agent 对话，进行细节控制和微调       |
| **看板操作**      | 可视化看板          | 点击任务 / 需求 / Commit 查看详情，拖拽调整优先级，标记状态 |
| **代码 / 文档浏览** | 文件浏览器          | 浏览任意仓库的文件内容、查看 Diff、切换 Commit 历史     |
| **通信记录查看**    | 通信面板           | 查看 Agent 间交互记录，筛选、搜索、追溯              |
| **评审操作**      | 评审面板           | 参与 DCP/TR 评审，查看评审材料，给出评审意见           |

### 8.2 主聊天面板（与主 Agent 交互）

**功能**：



* 用户输入项目需求（自然语言）

* 主 Agent 返回拆解结果、计划、进度报告

* 用户确认 / 修改计划

* 主 Agent 发起评审时，用户在此做决策

**交互示例**：



```
用户：我要做一个支持8路摄像头输入的NPU芯片，算力2TOPS，功耗≤2W

主Agent：已解析需求。项目类型：芯片设计（软硬件协同）。

&#x20;       建议激活角色：SE, TRL, EE, RTL, PNR, ANA, DFT, DV, FW, DRV, ALG, SIT, PQA, REL, TW

&#x20;       初步WBS拆解如下（共6阶段，42个工作包）...

&#x20;       是否确认启动项目？

用户：确认，但PNR角色先不激活，等RTL基本完成再说

主Agent：已调整。项目启动，初始化仓库...
```

### 8.3 Sub-Agent 聊天面板（与角色 Agent 直接交互）

**功能**：



* 用户选择任意活跃 Sub-Agent，进入专属聊天面板

* 用户可以提问、提需求、修改设计、检查细节

* 所有交互自动生成通信记录，绑定版本号

* Sub-Agent 的回复包含其当前 Commit 和相关交付物链接

**交互约束**：



* 用户直接修改 Sub-Agent 的产出物时，Sub-Agent 必须先评估影响，再执行修改

* 如果用户的修改与上游需求冲突，Sub-Agent 应提示冲突并建议同步通知主 Agent

* 用户的直接交互不绕过需求管理流程 —— 用户的指令会被记录为一条来源为 "user" 的需求

### 8.4 用户操作的版本锚定

用户的每一次操作（无论是对话还是看板操作）都记录**操作时主仓库的 Commit Hash**作为版本锚点。这意味着：



* 可以回答 "用户在哪个版本时提出了这个变更？"

* 可以回滚到用户操作前的状态

* 用户操作引发的连锁反应可以完整追溯

## 9. 可视化看板设计

### 9.1 看板设计理念

看板以 **Git Commit 为核心节点**，将项目的所有活动（任务完成、Agent 交互、需求变更、评审）都映射为 Commit 节点或 Commit 之间的关联边。用户看到的不是抽象的 "进度条"，而是真实的版本演化历史。

### 9.2 看板视图总览



```
┌────────────────────────────────────────────────────────────────────┐

│  \[项目名称]  \[阶段: 开发中]  \[进度: 68%]  \[活跃Agent: 12/15]     │

├────────┬───────────────────────────────────────────────────────────┤

│        │  🔍 搜索  📅 时间范围  🏷️ 角色筛选  📊 视图切换          │

│  导航  ├───────────────────────────────────────────────────────────┤

│        │                                                           │

│  ▸ 总览 │                  （当前视图内容）                          │

│  ▸ 阶段 │                                                           │

│  ▸ 角色 │                                                           │

│  ▸ 需求 │                                                           │

│  ▸ 通信 │                                                           │

│  ▸ 提交 │                                                           │

│  ▸ 评审 │                                                           │

│        │                                                           │

└────────┴───────────────────────────────────────────────────────────┘
```

### 9.3 核心视图详解

#### 9.3.1 总览视图（Dashboard）

**目的**：一眼掌握项目全局状态。

**包含模块**：



| 模块           | 内容                                 | 数据来源                          |
| ------------ | ---------------------------------- | ----------------------------- |
| 项目进度环形图      | 按 IPD 六阶段展示完成度                     | 各阶段已完成 Commit 数 / 计划 Commit 数 |
| 活跃 Agent 状态表 | 每个 Sub-Agent 的当前状态、最近 Commit、进行中任务 | Agent 注册信息 + 最新 Commit        |
| 关键路径甘特图      | 项目关键路径上的任务及依赖关系                    | WBS + 任务依赖关系                  |
| 风险预警列表       | 当前活跃的风险项（进度延迟、阻塞、质量问题）             | 风险登记册                         |
| 近期活动流        | 最近 20 条 Commit 和通信记录               | Git log + 通信记录                |
| 需求燃尽图        | 剩余需求数随时间变化                         | 需求状态历史                        |

#### 9.3.2 阶段视图（Phase View）

**目的**：按 IPD 阶段查看工作内容和进度。

**展示方式**：



* 顶部：六阶段时间轴，当前阶段高亮

* 中部：当前阶段的任务看板（Kanban 列：待开始 / 进行中 / 待评审 / 已完成 / 已阻塞）

* 每个任务卡片显示：任务标题、负责角色、关联需求 ID、最新 Commit Hash、进度条

* 点击任务卡片展开详情：子任务列表、Commit 历史、相关通信记录

#### 9.3.3 角色视图（Role View）

**目的**：查看每个 Sub-Agent 的工作状态和产出。

**展示方式**：



* 左侧：角色列表（头像 / 图标 + 角色名 + 状态指示灯）

* 右侧：选中角色的详情面板


  * 基本信息：角色描述、仓库地址、当前分支、最新 Commit

  * 任务列表：该角色的所有任务（按状态分组）

  * Commit 时间线：该角色的提交历史可视化（每个 Commit 是一个节点，显示 type 和 subject）

  * 通信记录：该角色发起和接收的通信

  * 产出物统计：代码行数、文档页数、测试用例数等

#### 9.3.4 需求视图（Requirement View）

**目的**：需求的全生命周期追踪。

**展示方式**：



* 需求列表（可按阶段 / 角色 / 优先级 / 状态筛选）

* 选中需求后展示**追溯链**：



```
需求创建 → 分配 → 任务拆解 → 各子任务Commit → 完成验证 → 关闭
```

每个节点可点击，跳转到对应的 Commit 或通信记录



* 需求依赖关系图（有向图，展示需求间的依赖）

#### 9.3.5 通信视图（Communication View）

**目的**：可视化 Agent 间的交互网络和需求传递。

**展示方式**：

**A. 交互拓扑图**（核心可视化）



* 节点：每个活跃 Agent 是一个节点（用户也是一个节点）

* 边：Agent 之间存在通信记录则有边


  * 边的粗细 = 通信频次

  * 边的颜色 = 通信类型（request = 蓝，response = 绿，escalation = 红，review = 紫）

  * 边的方向 = 通信发起方向

  * 鼠标悬停边 = 显示通信数量、最近一次通信主题

  * 点击边 = 展开该对 Agent 之间的所有通信记录列表

**B. 通信时间线**



* 按时间顺序展示所有通信记录

* 每条记录显示：时间、发起方→接收方、主题、状态、关联 Commit

* 可按角色、类型、状态筛选

**C. 需求传递链**



* 选中一条 request 类型的通信，展示完整的传递链：



```
发起方(commit A) → 需求内容 → 接收方(commit B) → 响应(commit C) → 确认(commit D)
```

每个 commit 节点可点击查看具体变更

#### 9.3.6 提交视图（Commit View）

**目的**：以 Git Commit 为节点的项目演化视图。

**展示方式**：



* **Git Graph 可视化**：所有仓库的 Commit 历史合并展示（主仓库 + 各 Sub-Agent 仓库），用不同颜色区分仓库

* 每个 Commit 节点显示：Commit Hash（短）、type 图标、subject、作者 Agent、时间

* 点击 Commit 节点展开详情：


  * 完整 Commit Message

  * 文件变更列表（Diff）

  * 关联的需求 / 任务 / 通信

  * 上下游 Commit 关系

* 支持按仓库、角色、Commit type、时间范围筛选

#### 9.3.7 评审视图（Review View）

**目的**：管理各 DCP/TR 评审点。

**展示方式**：



* 评审点时间线（CDCP → PDCP → TR4 → TR5 → GA）

* 每个评审点卡片：状态（未开始 / 准备中 / 待评审 / 已通过 / 已驳回）、评审材料清单、评审意见、决策结果

* 点击进入评审详情：所有相关交付物、Agent 的自评、评审 Checklist

### 9.4 看板交互规范



| 操作             | 效果                                 |
| -------------- | ---------------------------------- |
| 点击任意 Commit 节点 | 展开 Commit 详情，显示 Diff 和关联信息         |
| 点击任意通信边 / 记录   | 展开通信详情，显示完整内容和版本锚点                 |
| 点击需求           | 展示需求追溯链                            |
| 点击 Agent 节点    | 跳转到角色视图                            |
| 拖拽任务卡片         | 调整任务状态 / 优先级（生成一条用户操作记录，绑定 Commit） |
| 时间范围筛选         | 只显示指定时间范围内的 Commit 和通信             |
| 角色筛选           | 只显示指定角色相关的活动                       |

## 12. 技术实现建议

### 12.1 技术栈建议



| 层次            | 技术选型                                  | 理由                      |
| ------------- | ------------------------------------- | ----------------------- |
| **GUI 前端**    | Electron + React + TypeScript         | 跨平台桌面应用，生态成熟，适合复杂看板     |
| **看板可视化**     | AntV G6 / D3.js / React Flow          | 关系图、拓扑图、Git Graph 的成熟方案 |
| **状态管理**      | Zustand / Redux Toolkit               | 复杂应用状态管理                |
| **后端服务**      | Node.js + TypeScript / Python FastAPI | 与前端同语言或 AI 生态友好         |
| **Git 操作**    | isomorphic-git / libgit2 (node-git2)  | 纯 JS 或原生绑定，支持所有 Git 操作  |
| **Agent 运行时** | 自研 Agent 框架 / LangChain / LlamaIndex  | Agent 调度、上下文管理、工具调用     |
| **LLM 接入**    | OpenAI 兼容 API / 本地模型                  | 支持多模型切换                 |
| **本地存储**      | SQLite (better-sqlite3)               | 通信记录、需求索引、看板缓存          |
| **消息队列**      | 本地事件总线 (EventEmitter) / BullMQ        | Agent 间通信路由             |
| **文件监听**      | chokidar                              | 监听仓库变化，触发看板更新           |

### 12.2 关键实现难点与对策



| 难点                  | 对策                                              |
| ------------------- | ----------------------------------------------- |
| **多仓库 Git 操作一致性**   | 封装统一的 GitService，所有 Git 操作走服务层，确保原子性和错误处理       |
| **Agent 上下文管理**     | 每个 Agent 维护独立的会话历史，关键决策点做 snapshot，支持断点恢复       |
| **通信记录与 Git 的双向关联** | 通信记录写入时同步更新 Commit 索引；Commit 解析时提取 Refs 关联通信 ID |
| **看板实时更新**          | 文件监听 + 增量索引，Commit / 通信产生时触发看板数据刷新，不做全量重算       |
| **Sub-Agent 并发控制**  | 限制同时活跃的 Agent 数，按任务优先级调度，避免资源耗尽                 |
| **大仓库性能**           | 浅克隆 + 稀疏检出，Agent 只拉取需要的目录；Commit 历史分页加载         |

### 13.1 主 Agent（LPDT）System Prompt



```
\# 角色定义

你是 Project-Agent 系统的主Agent，承担IPD流程中的 LPDT（产品开发团队经理）角色。

你是项目的唯一入口和全局协调者，负责将用户需求转化为可执行的项目计划，并协调各Sub-Agent完成项目。

\# 核心职责

1\. \*\*需求解析\*\*：理解用户的项目需求，识别项目类型（软件/硬件/芯片/混合），明确关键指标和约束

2\. \*\*WBS拆解\*\*：按IPD六阶段（概念→计划→开发→验证→发布→生命周期）将项目拆解为工作包

3\. \*\*角色激活\*\*：根据项目类型确定需要激活的Sub-Agent角色，初始化各自仓库

4\. \*\*任务分配\*\*：将工作包分配给对应角色的Sub-Agent，明确验收标准和依赖关系

5\. \*\*进度监控\*\*：聚合各Sub-Agent的Commit和状态，维护项目级进度视图

6\. \*\*风险管理\*\*：识别进度延迟、依赖阻塞、质量问题，触发预警

7\. \*\*评审组织\*\*：在DCP/TR评审点汇总材料，组织评审

8\. \*\*主仓库维护\*\*：维护项目主仓库，汇总各阶段交付物

\# 工作规范

\## 需求处理流程

1\. 收到用户需求后，先输出需求理解摘要，确认无误后再拆解

2\. WBS拆解必须按IPD阶段组织，每个工作包包含：编号、标题、描述、负责角色、依赖、验收标准、预计产出

3\. 拆解完成后请用户确认，确认后再创建Sub-Agent和分配任务

\## 任务分配规范

\- 每个任务必须关联明确的需求ID

\- 必须说明任务的验收标准

\- 必须标注依赖关系（依赖哪些任务/需求/通信）

\- 分配后等待Sub-Agent确认接收

\## 进度管理

\- 每次收到Sub-Agent汇报后，更新项目进度

\- 每天（或每个关键节点）生成项目进度摘要

\- 发现阻塞超过24小时的任务，主动介入协调

\## Commit规范

你在主仓库的所有Commit必须遵循以下格式：

\- type: plan / review / comm / chore / docs

\- 必须关联需求ID、任务ID

\- 必须记录当前IPD阶段

\- body中说明本次变更的原因和影响

\## 你不可以做的事

\- 不直接编写具体模块的代码/设计（那是Sub-Agent的职责）

\- 不绕过Sub-Agent直接修改其子仓库内容

\- 不替用户做技术选型决策（提供建议，用户确认）

\- 不在未确认需求的情况下启动项目

\# 项目上下文

\- 项目名称：{project\_name}

\- 项目类型：{project\_type}

\- 项目描述：{project\_description}

\- 主仓库路径：{main\_repo\_path}

\- 当前IPD阶段：{current\_phase}

\- 激活角色列表：{active\_roles}

\# 输出格式要求

\- 项目计划使用Markdown表格输出

\- 进度报告使用结构化格式（总体进度 + 各角色状态 + 风险 + 下一步）

\- 所有引用的Commit使用短Hash（前8位）

\- 涉及需求/任务/通信时，必须标注ID
```

* Task: {task\_id}

* Phase: {current\_phase}

```
\- 所有通信自动记录，你可以在.agent/communications.log中查看

\## 自检要求

\- 代码类任务：编译通过 + 单元测试通过 + 代码规范检查

\- 设计类任务：设计规范检查 + 接口一致性检查 + 评审checklist

\- 文档类任务：格式检查 + 内容完整性检查 + 交叉引用验证

\- 自检结果必须写入Commit Message的body中

\## 你不可以做的事

\- 不修改其他Agent的仓库

\- 不跳过自检直接提交

\- 不在Commit中遗漏需求来源信息

\- 不擅自变更其他角色负责的接口/规格（需通过通信协商）

\# 项目上下文

\- 项目名称：{project\_name}

\- 项目类型：{project\_type}

\- 你的最新Commit：{latest\_commit}

\- 代码使用对应语言的代码块

```
